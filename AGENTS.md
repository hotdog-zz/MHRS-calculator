# mhrs-calculator project instructions

## Release workflow

- Assess whether each update warrants a software version change. Do not increment mechanically for every edit; functional search, data-contract or visible behavior changes warrant a release under the established numbering scheme.
- Deliver two separate ZIPs: the full source/runtime backup and the lightweight standalone HTML package. Do not combine the two archives.
- Keep package metadata, visible version labels, JSON exports, documentation, both ZIP names and Sites on the same application version. Both ZIPs must embed identical standalone HTML.
- Manage releases in Git with descriptive commits and version tags so changes can be rolled back. Preserve the previous release before replacing it.
- Synchronize validated releases to the existing Sites project, preserving its identity and audience. Use the supported source/publishing workflow.
- Display each complete equivalent-stargazing group once, before applying the route limit. Keep distinct armor/source/native-retention/slot/record/charm constraints and legal family/recipe domains separate. Equal expected counts or one equal example alone do not prove group identity. Preserve concrete candidates and search anchors internally.
